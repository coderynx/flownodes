# Outbound tunnels for carrying Web API calls

Research for issue #76, feeding the grilling ticket #77. It compares options and does not choose one.

**Question.** Which .NET-compatible ways exist to carry Web API calls from a Control Center to an Installation over a connection the Installation opens outward, and what does each cost?

**Context.** ADR-0029 (`docs/adr/0029-control-center-is-an-optional-client.md`, on the `docs/control-center` branch at the time of writing) says the Installation opens the link, so a site needs no inbound port, and that the Control Center reaches Installation data over that link through the public Web API. ADR-0001 requires everything to fit a single-Silo Raspberry Pi and to assume more than one Silo. ADR-0014 notes that Orleans gives Flownodes no cluster singleton. The Web API has no streaming endpoints today (no Server-Sent Events, WebSocket or SignalR code in `src/`), but the question asks whether streaming responses would pass.

Sources are primary only: Microsoft Learn, the `dotnet/yarp`, `dotnet/aspnetcore` and `grpc/grpc-dotnet` repositories, a sample by a YARP maintainer linked from the YARP issue, IETF RFCs and drafts, and the PostgreSQL manual. A claim without a citation is labelled as inference.

## The distinction that matters most

Every option has two layers, and the second one decides most of the cost:

1. **Carrier.** The long-lived outbound connection: a WebSocket, an HTTP/2 request whose request and response bodies form a duplex stream, a gRPC bidirectional stream, or a QUIC connection.
2. **What rides on it.** Either:
   - **A byte stream with real HTTP inside (connection-level).** The Installation's Kestrel treats each tunnel stream as an accepted connection and speaks ordinary HTTP/1.1 or HTTP/2 over it. On the Control Center side, `SocketsHttpHandler.ConnectCallback` returns the tunnel stream instead of a socket. Every HTTP feature that works on a socket works here unchanged, because HTTP is not re-implemented. David Fowler (ASP.NET) describes his YARP tunnel sample this way: "This plugs in at the connection layer so HTTP/1/2 and streaming protocols just work OOTB. These are handled by the SocketsHttpHandler and Kestrel." ([dotnet/yarp#1618](https://github.com/dotnet/yarp/issues/1618))
   - **Request and response messages (application-level).** A custom envelope (method, path, headers, body chunks, status) is sent as messages and replayed against the Web API on the far side. This re-implements HTTP framing, cancellation, trailers, flow control and upgrades, and it carries only what the envelope models.

Any carrier can carry either payload. The YARP sample, for example, runs the connection-level payload over both a WebSocket and an HTTP/2 duplex stream.

### How the connection-level variant plugs into ASP.NET Core

- **Installation side.** Kestrel accepts connections from every registered `IConnectionListenerFactory`. The `TransportManager` iterates the factories and binds an endpoint to the first one whose `IConnectionListenerFactorySelector.CanBind` accepts it (a factory without a selector accepts everything). `KestrelServerImpl` reverses the registration order, so the factory registered last is tried first ([TransportManager.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Servers/Kestrel/Core/src/Internal/Infrastructure/TransportManager.cs), [KestrelServerImpl.cs](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Servers/Kestrel/Core/src/Internal/KestrelServerImpl.cs), [IConnectionListenerFactorySelector](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Servers/Connections.Abstractions/src/IConnectionListenerFactorySelector.cs)). A tunnel transport that implements `CanBind` for its own endpoint type therefore sits beside the normal socket listener, and the local Web API port keeps working. Inference: the YARP sample's factory does not implement the selector, so used as written it would claim every endpoint.
- **Control Center side.** YARP lets an app replace the outbound `HttpMessageInvoker` through `IForwarderHttpClientFactory`. The sample overrides `ConfigureHandler` to set `SocketsHttpHandler.ConnectCallback`, which hands out a parked tunnel stream for a known host name ([YarpTunnelDemo `TunnelClientFactory.cs`](https://github.com/davidfowl/YarpTunnelDemo/blob/main/Frontend/Tunnel/TunnelClientFactory.cs)). A plain `HttpClient` with the same callback works without YARP.
- **Installation needs no YARP.** In the sample the "backend" runs YARP only because it proxies on to a third server. Here the tunnelled requests can land directly in the Installation's own Kestrel pipeline: authentication, authorisation and every endpoint stay as they are. Inference from the sample's `UseTunnelTransport`, which only registers a listener factory and a Kestrel endpoint ([WebHostBuilderExtensions.cs](https://github.com/davidfowl/YarpTunnelDemo/blob/main/Backend/Transport/WebHostBuilderExtensions.cs)).

## Options

### 1. WebSocket reverse tunnel

The Installation opens `wss://` to the Control Center, and the WebSocket becomes the carrier.

- **Raspberry Pi footprint.** `ClientWebSocket` is part of the .NET base library, and the Control Center end uses the ASP.NET Core WebSockets middleware, so the Installation gains no new package or native library. No primary source publishes per-connection memory or CPU figures for a Raspberry Pi. Inference: the cost is one TLS connection, the WebSocket buffers and, for the connection-level payload, one Kestrel connection per tunnel stream. Kestrel and `SocketsHttpHandler` already run in the Silo, so this cost should be small next to the Silo itself. Measure it in a prototype before relying on it.
- **Keep-alive.** RFC 6455 §5.5.2: "A Ping frame may serve either as a keepalive or as a means to verify that the remote endpoint is still responsive." §5.5.3 lets a Pong be sent unsolicited as a "unidirectional heartbeat" ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)). The .NET client has `KeepAliveInterval` and `KeepAliveTimeout`. The timeout waits for the peer's PONG and defaults to infinite, which means unsolicited PONGs only ([ClientWebSocketOptions](https://learn.microsoft.com/en-us/dotnet/api/system.net.websockets.clientwebsocketoptions?view=net-10.0)). The default client interval is 30 s, and the server middleware's `KeepAliveInterval` defaults to two minutes. Its `KeepAliveTimeout` defaults to disabled; when set, it aborts the connection if no pong arrives ([WebSockets in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0)). Dead-peer detection must therefore be configured explicitly on both ends.
- **Reconnection.** Nothing in `ClientWebSocket` reconnects. The app runs a connect loop: the YARP sample retries every 5 s with a "TODO: More sophisticated backoff" ([TunnelConnectionListener.cs](https://github.com/davidfowl/YarpTunnelDemo/blob/main/Backend/Transport/TunnelConnectionListener.cs)). The YARP design proposes retrying every 30 s on network failure or a 5xx response, and stopping on a 4xx ([yarp-tunneling.md](https://github.com/dotnet/yarp/blob/main/docs/designs/yarp-tunneling.md)).
- **Proxies and NAT.** WebSocket is "designed to work over HTTP ports 80 and 443 as well as to support HTTP proxies and intermediaries". A client behind a proxy issues `CONNECT` to it (RFC 6455 §1.1, §4.1). `ClientWebSocketOptions.Proxy` exists, and `HttpClient.DefaultProxy` reads `HTTPS_PROXY`, `ALL_PROXY` and `NO_PROXY` on Linux ([DefaultProxy](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclient.defaultproxy?view=net-10.0)). The Learn page says server pings exist "to ensure proxies keep the connection open". Because the connection is outbound TCP on 443, NAT needs no configuration, only traffic often enough to keep the mapping alive. Over HTTP/2 (RFC 8441, supported by Kestrel since .NET 7), a WebSocket uses an extended `CONNECT` instead of `GET` ([WebSockets in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0), [RFC 8441](https://www.rfc-editor.org/rfc/rfc8441)). `ClientWebSocketOptions.HttpVersion` and `HttpVersionPolicy` choose between the two.
- **Ordinary and streaming HTTP.** With the connection-level payload, yes, unchanged (see above). With a hand-rolled message envelope, only what the envelope models.
- **Multi-Silo.** The tunnel is a client socket owned by one process, so exactly one Silo must run the connect loop (see [Holding the link on one Silo](#holding-the-link-on-one-silo)). Requests arriving through it land on that Silo's Kestrel. Every Silo serves the whole Web API against shared stores, so inference says no forwarding is needed.
- **Maturity.** The pieces are fully supported framework APIs (`ClientWebSocket`, the WebSockets middleware, Kestrel transports, `ConnectCallback`). The tunnel glue is our code: there is no shipped Microsoft package.

### 2. YARP tunnelling

YARP has no shipped tunnel feature. What exists:

- **A design document**, merged in July 2022 as "Initial draft of tunneling spec" ([dotnet/yarp#1766](https://github.com/dotnet/yarp/pull/1766)) and now headed "These are archived design discussions. Information may be outdated and inaccurate." ([yarp-tunneling.md](https://github.com/dotnet/yarp/blob/main/docs/designs/yarp-tunneling.md)). Design points relevant here:
  - the back end opens a WebSocket to the front end, and the stream carries HTTP/2 "so that multiple simultaneous requests can be multiplexed";
  - the front end pings every 30 s at the WebSocket layer;
  - the front end treats each tunnel as a dynamic destination of a YARP cluster marked `IsTunnel`, and answers 502 when no tunnel is connected;
  - authentication goes through an app callback, and the samples would use client certificates.

  Open issues it records: "H2 perf becomes limited after 100 simultaneous requests. How does the front-end know to pair a second back-end connection?"
- **The feature request**, [dotnet/yarp#1618](https://github.com/dotnet/yarp/issues/1618), still open. Microsoft members said "it hasn't risen to be a priority". Users asked after the 2.0 release why tunnelling was missing, and in 2024 asked whether the design was "still just a design, nothing functional available?". The latest YARP release is 2.3.0 (February 2025), with no tunnel feature (`gh release list --repo dotnet/yarp`).
- **The sample** [davidfowl/YarpTunnelDemo](https://github.com/davidfowl/YarpTunnelDemo), written by an ASP.NET architect in about two hours by his own account ("I wrote it in 2 hours but it seems to work well enough", #1618), last committed 2022-09-21. The repository declares no license (GitHub API `license: null`), so code would need to be rewritten, not copied. What it shows:
  - **Two carriers.** It supports WebSocket and HTTP/2 duplex-stream carriers, with HTTP/2 as the default (`TunnelOptions.Transport = TransportType.HTTP2`). For HTTP/2 it posts a request with `Version = 2.0` and uses the request body and response body as the two directions ([HttpClientConnectionContext.cs](https://github.com/davidfowl/YarpTunnelDemo/blob/main/Backend/Transport/HttpClientConnectionContext.cs)).
  - **A connection pool.** The back end keeps up to `MaxConnectionCount = 10` tunnel connections open. Each carries one inner HTTP connection, and the front end parks them in a channel per host ([TunnelOptions.cs](https://github.com/davidfowl/YarpTunnelDemo/blob/main/Backend/Transport/TunnelOptions.cs), [TunnelExensions.cs](https://github.com/davidfowl/YarpTunnelDemo/blob/main/Frontend/Tunnel/TunnelExensions.cs)).
  - **Keep-alive and retries.** The WebSocket client sets `KeepAliveInterval = 5 s`, failed connects retry every 5 s, and the registration endpoint is unauthenticated ("Auth can be added to this endpoint").

Costs and behaviour are those of option 1 or option 4, depending on the carrier picked: YARP adds routing on the Control Center side, not a different transport. On the Installation, YARP is unnecessary (see above). It would add the `Yarp.ReverseProxy` package if used anyway.

- **Multi-Silo.** The design lets several back ends register for one YARP cluster and load-balances across them. A Control Center could therefore accept a tunnel from every Silo and spread calls. Inference: that would conflict with the requirement that only one Silo holds the link, unless the Control Center pins each Installation to one tunnel.
- **Maturity.** Design only and unsupported. YARP itself is a supported Microsoft library documented on Learn under ASP.NET Core ([YARP docs](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/yarp/config-files?view=aspnetcore-10.0)), and it is useful on the Control Center side as the forwarder.

### 3. gRPC bidirectional streaming

The Installation calls a bidirectional streaming method on the Control Center and keeps the call open. Requests flow down the response stream, and replies flow up the request stream.

- **Raspberry Pi footprint.** It adds `Grpc.Net.Client` and `Google.Protobuf` (and `Grpc.Tools` at build). gRPC is message-based: "The entire message is loaded into memory before gRPC can send it", messages above 85,000 bytes land on the large object heap, and Learn advises chunking large payloads into several messages ([gRPC performance](https://learn.microsoft.com/en-us/aspnet/core/grpc/performance?view=aspnetcore-10.0)). On a Raspberry Pi that matters for large responses unless bodies are chunked. No primary source gives Raspberry Pi figures.
- **Keep-alive.** HTTP/2 PING via `SocketsHttpHandler.KeepAlivePingDelay` and `KeepAlivePingTimeout`. The delay defaults to infinite, so pings are off ([KeepAlivePingDelay](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.keepalivepingdelay?view=net-10.0)). On the server side, Kestrel's `Http2.KeepAlivePingDelay` defaults to `TimeSpan.MaxValue` (off) and `KeepAlivePingTimeout` to 20 s ([Kestrel options](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/options?view=aspnetcore-10.0)). Learn warns that "Keep alive pings require the cooperation of the server". It also notes that "Long-running gRPC calls on the connection may still be terminated by the server or intermediary proxies for inactivity", so traffic on the stream itself still matters ([gRPC performance](https://learn.microsoft.com/en-us/aspnet/core/grpc/performance?view=aspnetcore-10.0)).
- **Reconnection.** Built-in retries do not cover this case. "Streaming RPCs that return multiple messages from the server won't retry after the first message has been received. Apps must add additional logic to manually re-establish server and bidirectional streaming calls." ([gRPC retries](https://learn.microsoft.com/en-us/aspnet/core/grpc/retries?view=aspnetcore-10.0)). Learn also lists, for streaming in place of unary calls: "A stream can be interrupted by a service or connection error. Logic is required to restart stream if there is an error." It adds that `RequestStream.WriteAsync` "is not safe for multi-threading", so concurrent replies need a producer/consumer queue ([gRPC performance](https://learn.microsoft.com/en-us/aspnet/core/grpc/performance?view=aspnetcore-10.0)).
- **Proxies and NAT.** gRPC requires end-to-end HTTP/2. gRPC-Web runs over HTTP/1.1 "in networks without complete support for HTTP/2" but drops "client streaming and bidirectional streaming" ([gRPC supported platforms](https://learn.microsoft.com/en-us/aspnet/core/grpc/supported-platforms?view=aspnetcore-10.0)). So there is no fallback for this option on a network that downgrades HTTP/2. L4 load balancers send every call on a connection to one endpoint ([gRPC performance](https://learn.microsoft.com/en-us/aspnet/core/grpc/performance?view=aspnetcore-10.0)). That does not hurt a single long-lived tunnel, but the Control Center must route a call to the replica that holds the Installation's stream.
- **Ordinary and streaming HTTP.** Not unchanged under a gRPC-native design. A gRPC method sends one message type each way ("Protobuf's support for unknown or conditional messages using `Any` and `oneof` can work around this limitation"), so HTTP requests must be modelled as an envelope. Headers, status, chunked bodies, cancellation and Server-Sent Events then need mapping, and WebSocket upgrades cannot pass. The alternative is to use the stream as an opaque byte pipe and run real HTTP inside it, the connection-level payload. That works, but it adds protobuf framing around what option 4 does natively. A YARP maintainer said WebSockets and gRPC "won't have significantly different performance characteristics in this streaming scenario" (Tratcher, #1618), and the YARP design's author added that the benefit of gRPC is "binary serialization of message contents rather than JSON", which a tunnel does not use (#1618).
- **Multi-Silo.** Same as option 1: one Silo holds the call.
- **Maturity.** grpc-dotnet is actively released (v2.84.0, 2026-09-21, `gh release list --repo grpc/grpc-dotnet`) and documented on Learn. Using it as an HTTP tunnel is our own design.

### 4. HTTP/2 and HTTP/3 reverse connections

**Standards first.** HTTP has no standard way for the side that opened the connection to act as the server.

- **HTTP/2** fixes the roles by who opened the connection: the client is "The endpoint that initiates an HTTP/2 connection" and "the TCP connection initiator" (RFC 9113 §2, §2.2). A server opens streams only through server push, which is tied to "a previous client-initiated request" (§8.4) ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)).
- **HTTP/3**: "HTTP/3 does not use server-initiated bidirectional streams … Clients MUST treat receipt of a server-initiated bidirectional stream as a connection error" (RFC 9114 §6.1) ([RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html)).
- **Drafts that would reverse the roles have all expired**: draft-bt-httpbis-reverse-http-01 (October 2023, ALPN `h2-reverse` and `h3-reverse`) ([datatracker](https://datatracker.ietf.org/doc/draft-bt-httpbis-reverse-http/)); draft-kazuho-httpbis-reverse-tunnel-00 (February 2024, extended `CONNECT`) ([datatracker](https://datatracker.ietf.org/doc/draft-kazuho-httpbis-reverse-tunnel/)); and the 2009 draft-lentczner-rhttp ([datatracker](https://datatracker.ietf.org/doc/id/draft-lentczner-rhttp-00.html)). None is implemented in .NET as far as these sources show.

**What works in .NET today** is the YARP sample's HTTP/2 carrier.

- **How it works.** The Installation sends an HTTP/2 `POST` whose request body stays open, and the request and response bodies form a duplex byte stream. Inside that stream the roles are reversed by convention: the Installation's Kestrel acts as server over it.
- **Raspberry Pi footprint.** No new dependency on the Installation: `SocketsHttpHandler` with HTTP/2 is built in. Kestrel's default HTTP/2 receive windows are 128 KB per connection and 96 KB per stream ([Kestrel options](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/options?view=aspnetcore-10.0)). They bound buffering per tunnel and can be lowered. Inference: about the same as option 1.
- **Keep-alive.** HTTP/2 PING frames are "a mechanism for measuring a minimal round-trip time from the sender, as well as determining whether an idle connection is still functional" (RFC 9113 §6.7). They are configured with `SocketsHttpHandler.KeepAlivePingDelay`/`Timeout` on the Installation and Kestrel `Http2.KeepAlivePingDelay`/`Timeout` on the Control Center (both off by default, see option 3).
- **Reconnection.** As option 1: our own loop.
- **Proxies and NAT.** It goes through an HTTPS `CONNECT` proxy like any HTTPS call ([DefaultProxy](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclient.defaultproxy?view=net-10.0)). But it needs HTTP/2 end to end, so a middlebox that terminates TLS and speaks HTTP/1.1 upstream breaks it. Inference: the gRPC-Web note above shows Microsoft treats such networks as real. In that case the WebSocket carrier over HTTP/1.1 is the fallback, which is why the sample offers both.
- **Ordinary and streaming HTTP.** Unchanged, because the payload is connection-level.
- **Multi-Silo.** As option 1.
- **Maturity.** Built on supported APIs. The duplex-POST pattern is not a documented Microsoft feature: it relies on `SocketsHttpHandler` streaming a request body while reading the response, which the sample enables with an immediate flush and a link to a runtime issue.

**HTTP/3 (QUIC)** as a carrier:

- **Raspberry Pi footprint.** It needs the native `libmsquic`: ".NET 7+ is only compatible with 2.2+ versions of libmsquic" and on Linux "you must manually install `libmsquic`" ([QUIC in .NET](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/quic/quic-overview)). Microsoft's Debian 12 repository publishes `libmsquic_2.6.3` for `arm64` and `armhf` ([packages.microsoft.com](https://packages.microsoft.com/debian/12/prod/pool/main/libm/libmsquic/)). This is an extra install step on the Raspberry Pi, outside the .NET runtime. If it is missing, Kestrel and `HttpClient` silently drop HTTP/3 ([Kestrel HTTP/3](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/http3?view=aspnetcore-10.0), [HttpClient HTTP/3](https://learn.microsoft.com/en-us/dotnet/core/extensions/httpclient-http3)).
- **NAT and proxies.**
  - Firewalls: "between 3% … and 5% … of networks block all UDP traffic", and for HTTP "this fallback is TLS over TCP" (RFC 9308 §2).
  - NAT bindings: "UDP applications can assume that any NAT binding or other state entry can expire after just thirty seconds of inactivity" (RFC 9308 §3.2) ([RFC 9308](https://www.rfc-editor.org/rfc/rfc9308.html)), so keep-alives need to be roughly twice as frequent as for TCP. `QuicConnectionOptions.KeepAliveInterval` exists ([QuicConnectionOptions](https://learn.microsoft.com/en-us/dotnet/api/system.net.quic.quicconnectionoptions?view=net-10.0)).
  - Proxies: Learn twice warns that "not all routers, firewalls, and proxies properly support HTTP/3" and recommends always configuring HTTP/1.1 and HTTP/2 alongside it. A UDP stream also cannot go through an HTTP `CONNECT` proxy. Inference: `CONNECT` tunnels TCP, and CONNECT-UDP proxies are rare on corporate networks.
- **Reverse use.**
  - QUIC itself is symmetric: a `QuicConnection` client can accept inbound streams ([QUIC in .NET](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/quic/quic-overview)). That makes a custom QUIC protocol possible, but it would not be HTTP/3.
  - Running Kestrel's HTTP/3 over an outbound QUIC connection would need a custom `IMultiplexedConnectionListenerFactory`, and no Microsoft sample exists. Inference.
  - The YARP design lists WebTransport only as "an interesting future protocol choice".
- **Maturity.** HTTP/3 is "fully supported in .NET 7 or later", and the `System.Net.Quic` APIs are stable from .NET 9 ([QUIC in .NET](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/quic/quic-overview)). A reverse HTTP/3 tunnel has no sample or standard.

## Holding the link on one Silo

This applies to every option, because each one is a client connection owned by one process. Inference: if two Silos both connected, the Control Center would see the same Installation twice, as the YARP design's load-balanced YARP cluster shows. Primary-source mechanisms available to Flownodes:

- **An Orleans grain as the owner.** A grain has "at most one activation … at any point in time", but the default directory "allows occasional duplicate activations during cluster instability". Orleans 10 adds a strongly consistent in-cluster directory (`AddDistributedGrainDirectory`) that "prevents duplicate grain activations even during cluster instability", but it "is currently in **preview**". An ADO.NET directory backed by PostgreSQL also exists (`Microsoft.Orleans.GrainDirectory.AdoNet`) ([Grain directory](https://learn.microsoft.com/en-us/dotnet/orleans/host/grain-directory)).
  - Keeping it alive: ADR-0014 states that Orleans "neither reactivates grains lost with a Silo nor gives us a cluster singleton". It already keeps grains alive with a reminder plus pings, and that pattern would apply.
  - Inference: the grain would ask its hosting Silo's tunnel service to connect, and deactivation would close it.
- **A PostgreSQL session-level advisory lock.** It "is held until explicitly released or the session ends" ([PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)). Each Silo tries `pg_try_advisory_lock`. The winner opens the tunnel, and a Silo crash drops its session and frees the lock. Inference: this needs a dedicated connection held open for the lock's lifetime, and a network partition between a Silo and Postgres must also close the tunnel.

Inference, either way: a duplicate-tolerant Control Center (accept the newest tunnel per Installation identifier, close the older one) makes a brief overlap during failover harmless. Failover time is then lock or reminder detection plus one reconnect.

## Not covered in depth

- **Azure Relay Hybrid Connections.** The YARP design names [Azure Relay](https://learn.microsoft.com/azure/azure-relay/relay-what-is-it) as the model for the feature, and an ASP.NET Core server for it exists ([Azure/azure-relay-aspnetserver](https://github.com/Azure/azure-relay-aspnetserver), cited in #1618). It is a hosted cloud service, while ADR-0029 makes the Control Center self-hostable and offline-capable, and ADR-0001 rules out a required cloud service. Inference.
- **Third-party libraries** built on the YARP sample (UFX.Relay, FlorianGrimm's fork, both mentioned in #1618) are not primary sources and are not assessed here.

## Comparison

| | WebSocket tunnel | YARP tunnelling | gRPC bidi stream | HTTP/2 duplex stream | HTTP/3 (QUIC) |
|---|---|---|---|---|---|
| New dependency on the Installation | none (BCL + Kestrel) | none needed (YARP only on Control Center) | `Grpc.Net.Client`, `Google.Protobuf` | none | native `libmsquic` package |
| Raspberry Pi footprint (no published figures) | low; measure | as its carrier | higher for large messages (whole message in memory) | low; measure | extra native library, UDP keep-alives |
| Keep-alive | WebSocket ping/pong; timeouts off by default | 30 s WS ping in design | HTTP/2 PING; off by default; needs server cooperation | HTTP/2 PING; off by default | QUIC PING; NAT may drop after 30 s idle |
| Reconnection | own loop | own loop (design: 30 s, stop on 4xx) | own loop; built-in retries do not apply | own loop | own loop |
| Through HTTP proxies | yes, `CONNECT` on 443; HTTP/1.1 fallback | as carrier | only if HTTP/2 end to end; no bidi in gRPC-Web | only if HTTP/2 end to end | no; 3–5 % of networks block UDP |
| HTTP and streaming responses unchanged | yes with connection-level payload | yes | no with an envelope; yes only as a byte pipe | yes | only with a custom multiplexed transport |
| One Silo holds the link | grain or advisory lock | design balances across many back ends | grain or advisory lock | grain or advisory lock | grain or advisory lock |
| Maturity | supported APIs; our glue | design archived; issue open; unlicensed sample | supported library; our tunnel design | supported APIs; undocumented pattern | supported HTTP/3; no reverse standard (drafts expired) |
