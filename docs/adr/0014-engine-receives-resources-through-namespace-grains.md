# The Engine receives Resources through Namespace grains, level-triggered

Every Resource message from the Registry carries the whole Spec and a per-Namespace sequence number, and is delivered to one grain per Namespace, which forwards it to the Resource's grain, detects lost messages and keeps the Namespace's Resource grains alive. Missed messages are repaired by resyncing the whole Namespace from the Registry rather than by guaranteeing every message arrives. We chose this level-triggered design over pushing each change to its grain because Orleans neither reactivates grains lost with a Silo nor gives us a cluster singleton, and because with messages that can be duplicated, reordered or lost, "converge on the latest state" is the only guarantee that holds across Silo failures and a wiped Engine database.

## Consequences

- The Registry keeps a gap-free counter per Namespace, incremented once per Resource message inside the apply transaction. `ResourceApplied` carries Namespace, Kind, name, `uid`, Generation, `seq` and Spec; `ResourceDeleted` carries the same without the Spec. Grains apply a message only if its `seq` is newer than the last they applied, which also discards stale messages about a deleted and re-created Resource.
- Resource grains are keyed `"{namespace}/{name}"` with one grain type per Kind; the `uid` is grain state, and a new `uid` means tear down, then reconcile from scratch. Asset Types are grains too: the Registry publishes Assets unexpanded and the Asset grain merges its Asset Type's definition at runtime.
- The Namespace grain requests a resync on activation, on a `seq` gap and every 15 minutes by default. The Registry answers with every current Resource and a closing list of refs; the Engine tears down grains not on it and every grain re-sends its Status.
- One Orleans reminder per Namespace grain keeps it alive; it pings its member grains every 10 seconds, which reactivates those lost with a Silo. Worst-case failover is about one reminder period plus one ping.
- Each Silo asks the Registry for the name of every Namespace when it starts and then every 5 minutes by default, and wakes each Namespace's grain. A grain with live state ignores the wake; one with no state, or marked deleted, requests a resync. So a wiped Engine database, a fresh Engine against a populated Registry, or a lost request recovers within one listing interval, with no Silo restart. With N Silos the Registry answers N lists per interval, and waking a grain twice is harmless.
- Grains reconcile independently of each other. A grain registers as a dependent with every grain it references and is notified when that grain changes or its readiness changes; until then it reports a condition such as `ConnectionNotReady`.
- Each grain persists its `uid`, last reconciled Spec and Generation, last applied `seq` and last reported Status. Runtime values stay in memory, except Asset Data Point values written by a Flow, which have no other source to restore them.
- Status reaches the Registry as `StatusReported`, sent only on change and debounced for fast-changing parts such as Discoveries. The Registry stores it beside the Resource and keeps it only if the `uid` matches and the Status sequence is newer, so `flowctl get` never touches the Engine. `observedGeneration` means the Engine has picked up that Generation; whether reality matches is the `Ready` condition.
- Secret values are encrypted with one installation key supplied by the deployment, identically on every Silo, and stay encrypted in the outbox, the queues and grain storage.
