# An optional Control Center manages Installations; each Installation stays authoritative and complete

Managing several Installations from one place, and building apps for a domain, belong to the Control Center, a separate application that uses only the public API of each Installation. It owns no Resource. Each Installation's Registry stays the only source of truth (ADR-0002, ADR-0004), and an Installation works fully without a Control Center (ADR-0001). We rejected a central manager that holds configuration no Installation has, because an Installation could then no longer be rebuilt from its own Manifests. We also rejected a manager that becomes the only management path, because a site that loses its link would lose alarm handling. Apps live in the Control Center, not in Flownodes, so that Flownodes stays a core with one plain, generic web UI.

## Consequences

- The built-in web UI ships in v1 alongside `flowctl` and covers every Viewer, Operator and Engineer task within one Installation; it builds and renders no apps. `flowctl`, the Web API and the web UI are never locked out in favour of a Control Center.
- The Control Center changes an Installation the way any client does: it applies Manifests to a Namespace in it. Distributing an Asset Type to many Installations means applying it to a named Namespace in each one; nothing is shared across Namespaces (ADR-0005). Long-term history stays with Integrations to external databases, not in the Control Center.
- Each Installation generates a permanent identifier when it first starts. The Control Center addresses an object by Installation, Namespace, Kind and name.
- The Installation opens the link to the Control Center, so a site needs no inbound port. An Administrator enrols an Installation by entering a one-time join token issued by the Control Center, which carries its address. An Installation has at most one Control Center. The link is an installation-wide setting managed by an Administrator, not a Resource, so rebuilding an Installation from its Manifests never enrols it anywhere. When the link drops, the Control Center's view goes stale and the Installation carries on.
- An Installation signs in only its own Users and Service Accounts. Signing people in through an external OIDC provider is the Control Center's job, not Identity's. Apps reach Installation data through the Control Center, over the link.
- Background work, such as fleet views, runs as a Service Account: an identity for a program, created and disabled by an Administrator, that signs in with the OAuth2 client credentials grant and a secret shown once. A Service Account holds Viewer, Operator or Engineer Role Grants in Namespaces and never the Administrator role.
- A new per-Namespace Viewer role sees configuration, live state and Alarms and changes nothing, so a Control Center's background credential can be read-only.
- The Control Center is self-hostable and can run on a site's own network, so apps keep working without an internet connection. A first Control Center only reports each Installation's Flownodes version and Integrations; upgrading an Installation remotely needs its own design.
