# Clients receive live state through a server-sent events stream from the Engine

A client opens one server-sent events stream per Namespace from the Engine, which sends a snapshot of the live state it covers and then every change: Data Point values with Quality and source timestamp, Alarms, Flow Execution progress and Resource Status. A reconnect gets a fresh snapshot rather than a replay of what was missed, the same "converge on the latest state" guarantee as ADR-0014. The stream is a Web API feature for every client, `flowctl` and the Control Center as well as the web UI. We chose server-sent events over SignalR because a stream is a plain HTTP response: the browser's `EventSource` sends the session cookie (ADR-0030), `flowctl` reads it like any other response, and it crosses the Control Center's HTTP tunnel unchanged, whereas SignalR is its own protocol, usually over WebSockets, and needs its library in every client. Pushes only go from server to client; writes, acknowledgements and Actions stay ordinary requests. We rejected polling as too slow for Alarms and wasteful on a Raspberry Pi (ADR-0001).

## Consequences

- The stream is `GET /api/v1/engine/namespaces/{namespace}/live`, narrowed by repeatable `asset`, `device` and `flow` parameters and by `topic` (`dataPoints`, `alarms`, `executions`, `resources`). Without filters it covers the whole Namespace. The `alarms` topic always covers the whole Namespace, because an Operator must see every Alarm wherever it is raised. A client changes its filters by reconnecting. The web UI waits about 300 ms for a selection to settle before it reconnects, and doesn't show that reconnect as a lost connection.
- Opening a stream needs any role in the Namespace, as the matching reads do. The Engine closes a stream when its replica of Role Grants loses the caller's grant, and when the access token the stream opened with expires, so the client reconnects with a fresh token and is checked again. Modules stay bearer-only without checking tokens mid-stream.
- Events reuse the read DTOs: `dataPoint` (with its Asset or Device), `alarm`, `execution` and `resource`. An Alarm's last event is an `alarm` with its final state, `ended` or `retired`, so a client can say why it left the live list. `removed` says an object was deleted or left the stream's scope, `ready` ends the snapshot, and `reset` tells the client to drop its state because a fresh snapshot follows. A `:keepalive` comment every 15 seconds keeps proxies from closing an idle stream. Every event's `data` is one JSON object. There are no event ids and no `Last-Event-ID` replay: the Engine keeps no event log, and missed history belongs to the Alarm history and the Flow Execution list.
- Data Point changes are coalesced per Data Point to the latest value at most every 250 ms, a server default a client cannot raise. A Quality change is sent at once.
- A Flow Execution sends an event when it starts, at each checkpoint with its current Node and state, and when it ends. Variables stay on `GET …/executions/{id}`.
- Resource Status comes from the Engine's grains, which produce it and receive every `ResourceApplied` and `ResourceDeleted`, so the Registry has no stream of its own. Over plain `http://` a browser uses HTTP/1.1 and opens at most 6 connections per origin across all tabs, and a second stream per tab would hang the fourth tab. The Engine's view can briefly be ahead of the Status the Registry has stored.
- A stream lands on any Silo, and the grains it watches live on any Silo. Each Silo keeps one live hub per Namespace with open streams; the hub subscribes to that Namespace's grains with Orleans grain observers, every stream on the Silo reads from it, and it unsubscribes when its last stream closes. Cross-Silo traffic grows with the number of Silos, not the number of clients. Observers expire and are lost when a grain moves to another Silo, so the hub re-subscribes on the 10-second ping of ADR-0014 and sends its streams a `reset`. We rejected Postgres `NOTIFY`, which writes to the database for every value change, and Orleans Streams, which need a pub-sub store and add a second messaging mechanism.
- Each Silo caps its open streams (default 200) and answers `503` with `Retry-After` past the cap.
- There is no stream across Namespaces. The web UI shows Alarms per Namespace, and the Installation Summary polls `GET /api/v1/engine/installation` for Silo load.
- `flowctl watch` takes the stream's filters as `--asset`, `--device`, `--flow` and `--topic`, prints one line per change, or newline-delimited JSON with `-o json`, and reconnects with backoff, showing the `reset` and the fresh snapshot.
