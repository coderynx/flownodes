# The web UI signs in through a backend-for-frontend; the browser never holds a token

The built-in web UI signs in through a backend-for-frontend in a new `Web` package, which also serves the UI's static files from the same origin as the Web API. `Web` is a confidential OIDC client of Identity: it runs authorization code with PKCE on the server, keeps the User's access and refresh tokens in a server-side session, and gives the browser only an HttpOnly session cookie. On every request that carries the cookie and no `Authorization` header, `Web` attaches the session's access token as a bearer token, so the Registry, the Engine and Identity keep authenticating bearer tokens only and never see a cookie. We chose this over a public client holding tokens in JavaScript, which exposes them to any script on the page, a large surface once the Manifest editor and graph libraries load, and which cannot send a token on `EventSource` or WebSocket connections without putting it in the query string. We also rejected a backend that obtains tokens and hands them to the browser, which costs as much as a backend-for-frontend and exposes the tokens as a public client does. And we rejected teaching every resource server to accept cookies, which would spread the UI's session and Data Protection keys into every module.

## Consequences

- `Web` references no module and reaches Identity only over the OIDC protocol through the `Flownodes:Identity:Authority` setting, as `flowctl` does (ADR-0026). The host reaches it through its `Bootstrap` (ADR-0018).
- It is built from what ASP.NET Core and OpenIddict ship: `AddOpenIdConnect` with `SaveTokens` signing in to `AddCookie`, a `SessionStore` over `IDistributedCache` backed by `Microsoft.Extensions.Caching.Postgres`, and Data Protection keys persisted to Postgres. The refresh step and the CSRF check are the only code `Web` owns. It takes no third-party token-management library.
- The session lives in `Web`'s own Postgres schema, beside its Data Protection keys. The cookie carries only the protected session id, so every Silo can serve every session and the cookie stays small.
- The cookie is `__Host-flownodes`, HttpOnly, `Secure` and `SameSite=Lax`, so a pasted link opens the UI already signed in. `Web` attaches the token to a POST, PUT, PATCH or DELETE only when the request carries the `X-Flownodes-Client` header, which a cross-site form cannot send. GET requests, `EventSource` streams included, need no header, and requests with their own bearer token skip the check.
- `Web` refreshes the access token when the cookie is validated close to the token's expiry. A session lasts as long as Identity keeps refreshing it, with no idle timeout, so a control-room screen left open stays signed in. Disabling a User revokes their refresh tokens (ADR-0026), so their session ends within one access token lifetime. The other modules already reject them at once. A long-lived push stream authenticates only once, so it must close when its User is disabled.
- Signing out deletes the session, revokes its refresh token at Identity's revocation endpoint, expires the cookie and redirects through Identity's end-session endpoint, which clears Identity's own sign-in cookie. Signing in again then asks for the password, even on a shared PC.
- Identity gains OpenIddict's authorization, end-session and revocation endpoints, all served through its existing sign-in page. On first start it seeds a confidential `web` client, which may use only the authorization code and refresh token grants. Both sides derive the client's secret from the installation key, so the deployment supplies nothing new.
- The UI learns who is signed in from `/bff/session`, which returns the User's id and name, or 401. What the User may do comes from the Web API, as for every client, because Identity carries no authorisation in tokens (ADR-0026).
- Detaching modules is not offered in v1, but nothing here stands in its way. When the Registry or the Engine runs in another process, `Web` forwards the UI's `/api/v1` calls to it with YARP after attaching the token. That forwarding is not built until a deployment needs it (ADR-0024).
