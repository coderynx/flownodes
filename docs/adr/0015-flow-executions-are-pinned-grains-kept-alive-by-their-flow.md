# Flow Executions are pinned grains kept alive by their Flow

Each Flow Execution is its own grain, keyed `"{namespace}/{flow}/{executionId}"`, that runs the Generation of its Flow it started on and is reactivated after a Silo failure by its Flow grain pinging it, not by an Orleans reminder. We chose pinning over cancelling or migrating running Executions when a Flow changes because cancelling breaks the promise of ADR-0006 on every small edit and migrating by Node id silently changes what a half-finished Execution does. We chose the ping chain over a reminder per wait because it reuses the level-triggered liveness of ADR-0014 and adds no storage writes per wait, which matters on a Raspberry Pi (ADR-0001).

## Consequences

- An Execution's checkpoint is its row in an Engine-owned table: state, current Node, variables, pinned Generation and Spec, trigger and deadline. It is written after every completed Node, and it is also the record Engineers list, so there is one write per Node and no second copy. The Flow grain does not persist its active Executions; it queries them by its `uid` on activation, so a lost ping never orphans one.
- The Flow grain pings its active Executions on every ping from its Namespace grain, and each Execution sets an in-memory timer for its persisted deadline. Worst-case failover is about one reminder period plus two pings.
- Deleting a Flow, or re-creating it with a new `uid`, cancels its running Executions at their next checkpoint; a Node in progress is not interrupted. A pinned Execution can outlive what its Generation references, so such a Node fails with `ReferenceMissing`.
- An Execution has exactly one current Node in v1: a branch Node takes one outgoing edge, and there is no fan-out or join. Cycles are allowed, capped by a per-Flow limit on Node steps (default 1,000) and on variable size (default 64 KB).
- The Flow's Execution Mode decides what a trigger does while an Execution is running: `single` (the default) drops it and records the drop, `restart` cancels and starts again, `queue` persists it in the Flow grain and runs it next, and `parallel` runs both. `queue` and `parallel` are capped per Flow (default 10).
- Triggers are at-most-once until the Execution's first checkpoint, then at-least-once per ADR-0006. An Event or "on any change" Data Point trigger arriving during failover is lost. A condition trigger fires on the transition from false to true, not on Quality changes, and the Flow grain persists each condition's last result, so a transition that happened during an outage fires once, late, on reactivation.
- Schedule triggers are a cron expression in an IANA time zone, defaulting to an installation-wide one from the deployment. DST gaps fire at the next valid time and repeated hours fire once.
- Waits are absolute UTC deadlines. An overdue wait continues as soon as the Execution reactivates and records its lateness; past an optional `maxLateness` it takes its timeout or error edge instead, and a missed schedule fire past `maxLateness` is skipped and recorded. Every wait for a Data Point condition or an Event has a mandatory timeout; a condition is re-checked on resume, an Event that fired while the Execution was down is missed.
- A Node has a timeout (default 30 s) and a retry policy (default none). On failure it follows its `error` edge if wired, otherwise the Execution ends `Failed` with the Node, error and attempt count. An Action on a Connection that is not ready waits for it within the timeout, then fails with `ConnectionNotReady`. A `bad` Quality value is not a failure.
- Executions are runtime state (ADR-0002), so they are not in the Flow's Status, which carries only the active count and the last result. The Engine serves them on its own HTTP endpoint (ADR-0012), keeping the last 100 finished Executions per Flow or 7 days, whichever keeps more. Operators can list and inspect them; Engineers can also cancel one or all, and start one manually with a given trigger payload.
