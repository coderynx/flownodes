# The web UI is a React single-page app built with Vite and served by `Web`

The built-in web UI is a TypeScript single-page app written in React and built with Vite. `Web` serves its build output as static files from the same origin as the Web API (ADR-0030), so production runs no Node.js. The UI reaches Flownodes only through the public Web API and its push channel, the same way `flowctl` and the Control Center do, and it renders in the viewer's browser rather than on the Installation. We rejected Blazor WebAssembly. Its runtime alone is about 2 MiB compressed, roughly 17 s at 1 Mbit/s on a slow site network, it runs interpreted .NET on weak kiosk browsers, and it still needs JavaScript interop for the Manifest editor and the graph. We also rejected server-rendered Razor with htmx. It renders every interaction and every pushed value on the Installation, which on a Raspberry Pi shares the CPU with the Engine. It pushes HTML that no other client can use, and it tends to call handlers in process instead of the Web API, against ADR-0018. Every option ends up with a JavaScript editor and layout library, so neither alternative keeps the UI free of a JavaScript toolchain. Among the JavaScript frameworks, the editor and graph libraries outweigh the framework's own size, so we chose React because coding agents write it most reliably.

## Consequences

- The Manifest editor is CodeMirror 6 with `@codemirror/lang-yaml` and `codemirror-json-schema`, loaded only on the routes that edit. Monaco with `monaco-yaml` weighs 1.2–3.2 MiB against CodeMirror's 310 KiB. Validation in the editor is advisory: validation at apply (ADR-0009) and `?dryRun=true` stay the authority. If `codemirror-json-schema` falls behind, we wrap it or fork it.
- A Flow is drawn read-only by `@xyflow/react`, at positions computed by `@dagrejs/dagre`, because a Manifest carries no Node coordinates. elkjs is an option only if real Flows lay out badly. Its EPL-2.0 or GPL-3.0-or-later licence is compatible with AGPL-3.0, but it is 434 KiB.
- The host's OpenAPI document is generated at build time with `Microsoft.Extensions.ApiDescription.Server` and committed. CI fails when it is stale, as it does for generated handler code. Responses must be described correctly, and integers are emitted with strict number handling, so generators type them as numbers. Serving the document outside Development is a separate decision.
- The UI's client is the type file that `openapi-typescript` generates from that document, checked in and checked for drift in CI, used through `openapi-fetch`. One shared client sends `X-Flownodes-Client` and same-origin credentials, so no page handles the CSRF header or a token.
- The SPA lives in `packages/web/Web.Client/` as a plain Vite project, beside the `packages/web/Web` C# project. Building `Web` runs `npm ci` and `npm run build` into its `wwwroot`, so `MapStaticAssets` compresses and fingerprints the files. Setting `-p:SkipWebClient=true` skips that step for backend-only builds. The client has its own CI job. There is no `.esproj`, so `dotnet build` does not depend on the JavaScript project system.
- Node.js is needed in development and CI, never on an Installation.
- In Development, the AppHost runs the Vite dev server as a resource, and `Web` forwards every path outside `/api`, `/bff` and Identity's endpoints to it, hot reload included. The browser always talks to the host's origin, so the session cookie, the OIDC redirect and the CSRF check behave as they do in production.
- The C# analyzers, `scripts/format.sh` and the architecture tests do not reach TypeScript. The frontend needs its own coding standard and CI checks, decided separately, as are the component library, routing and end-to-end testing.
